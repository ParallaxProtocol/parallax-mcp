# PIP-0005: Robust UPnP NAT Traversal

Description: Overhaul the UPnP NAT implementation with custom SSDP discovery, broader device compatibility, improved port mapping resilience, and comprehensive operator logging.
Author: Parallax Protocol Team
Status: Scheduled for v1.1.2
Type: Standards Track
Category: Networking
Created: 2026-04-05

## Abstract

This PIP overhauls the UPnP NAT traversal implementation in the Parallax p2p networking stack. The existing implementation, inherited from go-ethereum, relies on the `goupnp` library for SSDP device discovery, which fails on a wide range of consumer routers due to restrictive search targets, fragile multi-socket multicast, and strict validation of optional UPnP actions. This proposal replaces the SSDP discovery layer with a custom implementation that sends M-SEARCH requests via both multicast and unicast using a single socket, searches for all standard IGD device types, tolerates routers that omit optional SOAP actions, supports IGDv2 `AddAnyPortMapping` with retry-and-fallback for IGDv1, and adds comprehensive logging so node operators can diagnose NAT issues without external tools.

## Motivation

Node reachability is critical for a healthy peer-to-peer network. Nodes behind NAT that cannot accept inbound connections become free-riders: they consume peer slots on reachable nodes without contributing inbound capacity. UPnP is the most widely supported automatic port-mapping protocol on consumer routers, but the inherited go-ethereum implementation fails to discover or use it on many common devices for several compounding reasons:

1. **Narrow SSDP search targets.** The `goupnp` library searches only for `WANConnectionDevice:1` and `WANConnectionDevice:2`. Many routers (notably Huawei, TP-Link, and various ISP-provided devices) only respond to searches for the root device type `InternetGatewayDevice:1`. This causes discovery to fail silently.

2. **Fragile multicast socket handling.** `goupnp` creates one UDP socket per local IPv4 interface address, then fans out requests via `errgroup`. On Linux systems with multiple interfaces (Docker, VPN, Tailscale), error propagation between sockets can cascade and cancel working connections. Consumer firewalls (`ufw`, `iptables`, `nftables`) commonly block multicast but not unicast, leaving no fallback path.

3. **Mandatory optional action.** The `GetNATRSIPStatus` SOAP action is used as a gate before accepting a discovered device. This action is optional in the UPnP IGD specification, and many routers return SOAP fault 401 ("Invalid Action"). The existing code treats this as "NAT is not enabled" and silently discards the device, even though port mapping works perfectly.

4. **Silent error swallowing.** `AddMapping` returned `nil` instead of propagating the error when internal address resolution failed, causing the caller to log "Mapped network port" for mappings that were never created.

5. **No port conflict handling.** If the requested external port is already mapped by another application, the mapping fails with no retry or alternative port selection.

6. **Insufficient logging.** Discovery, mapping, and error paths produced no output at default log levels, making NAT issues invisible to operators.

## Specification

### Custom SSDP Discovery

Replace `goupnp.DiscoverDevices()` with a custom `ssdpDiscover()` function that:

- Opens a **single UDP socket** bound to `0.0.0.0:0`, matching the behavior of `miniupnpc` (the de facto standard UPnP client).
- Sends M-SEARCH requests to **both** the standard multicast group (`239.255.255.250:1900`) **and** the default gateway via unicast. This ensures discovery works even when multicast is blocked by local firewalls.
- Always sets the `HOST` header to `239.255.255.250:1900` as required by the UPnP specification, regardless of the actual destination address.
- Searches for **four** SSDP targets:
  - `urn:schemas-upnp-org:device:InternetGatewayDevice:1`
  - `urn:schemas-upnp-org:device:InternetGatewayDevice:2`
  - `urn:schemas-upnp-org:device:WANConnectionDevice:1`
  - `urn:schemas-upnp-org:device:WANConnectionDevice:2`
- Sends each M-SEARCH **3 times** per target per destination for UDP reliability.
- Waits **5 seconds** for responses (up from goupnp's 2 seconds).
- Collects unique `Location` URLs from responses, then fetches device descriptions via `goupnp.DeviceByURL()` and walks the device tree for IGD services.

### Tolerant NAT Status Check

Change `natEnabled()` to treat SOAP errors from `GetNATRSIPStatus` as "NAT is probably enabled" rather than "NAT is disabled":

| `GetNATRSIPStatus` Result | Behavior |
|---|---|
| Success, `nat=true` | Accept device |
| Success, `nat=false` | Reject device (explicitly reports no NAT, e.g. bridge mode) |
| SOAP error (401, 501, etc.) | **Accept device** (action not supported, does not imply no NAT) |

If a device is accepted but NAT is truly unavailable, `AddPortMapping` will fail later with a clear error. This matches `miniupnpc` behavior, which does not call `GetNATRSIPStatus` at all.

### Updated AddMapping Interface

Change the `nat.Interface.AddMapping` signature from:

```go
AddMapping(protocol string, extport, intport int, name string, lifetime time.Duration) error
```

to:

```go
AddMapping(protocol string, extport, intport int, name string, lifetime time.Duration) (uint16, error)
```

The returned `uint16` is the actual external port assigned by the router, which may differ from the requested port when using `AddAnyPortMapping` or random port fallback.

### IGDv2 AddAnyPortMapping Support

For routers that support IGDv2 `WANIPConnection:2`, use the `AddAnyPortMapping` SOAP action, which allows the router to automatically select an available external port if the requested one is in use.

### Retry and Random Port Fallback for IGDv1

For IGDv1 routers that only support `AddPortMapping`:

1. Retry the requested external port up to **4 times** (initial attempt + 3 retries).
2. If all retries fail, attempt **3 random ports** in the range 10000-65535.
3. Log each attempt at DEBUG level and the final failure at WARN level.

### Bug Fix: Error Propagation in AddMapping

The original `AddMapping` returned `nil` when `internalAddress()` failed:

```go
ip, err := n.internalAddress()
if err != nil {
    return nil  // BUG: swallows error
}
```

This is corrected to properly propagate the error.

### Comprehensive Logging

Add structured logging at appropriate levels throughout the NAT subsystem:

| Component | Level | What is logged |
|---|---|---|
| SSDP discovery | INFO | Search start, device locations found, final result |
| SSDP discovery | DEBUG | Multicast/unicast destinations, per-target sends, response parsing |
| Device inspection | DEBUG | Friendly name, all service types found, service matching |
| NAT status | DEBUG | GetNATRSIPStatus result or SOAP error |
| External IP | INFO | Resolved external IP address |
| External IP | WARN | Failure to resolve external IP |
| Port mapping | DEBUG | Full mapping parameters (protocol, ports, internal IP, lifetime) |
| Port mapping | WARN | Mapping failure after all attempts exhausted |
| Port mapping | INFO | Successful mapping, random port assignment |
| Map lifecycle | INFO | Mapping creation and deletion |
| Map lifecycle | WARN | Refresh failures |
| Server setup | INFO | NAT mechanism selected, port mapping goroutines started |
| Server setup | WARN | External IP discovery failure |
| Failure hint | WARN | Actionable hint mentioning ufw/iptables/nftables when discovery fails |

### Dependency Upgrade

Upgrade `github.com/huin/goupnp` from v1.0.3 to v1.3.0 for context-aware SOAP operations and improved XML parsing. SSDP discovery from goupnp is no longer used; only `DeviceByURL()` and the IGD service client types are retained.

## Rationale

### Why Replace goupnp's SSDP?

The `goupnp` library's SSDP implementation creates multiple UDP sockets (one per interface IP) and coordinates them via `errgroup`, which introduces failure cascading on multi-interface Linux hosts. It also only supports multicast, with no unicast fallback for firewalled environments. A single socket on `0.0.0.0` with dual multicast+unicast delivery matches `miniupnpc`'s proven approach and eliminates an entire class of socket-related failures.

### Why Search for InternetGatewayDevice?

The UPnP IGD device hierarchy is: `InternetGatewayDevice` > `WANDevice` > `WANConnectionDevice` > services. Some routers only advertise the root device type in SSDP responses, not sub-device types. Searching only for `WANConnectionDevice` (as goupnp does) misses these routers entirely. `miniupnpc` searches for `InternetGatewayDevice`, which is why it discovers devices that goupnp cannot.

### Why Tolerate GetNATRSIPStatus Failures?

The UPnP IGD specification lists `GetNATRSIPStatus` as part of the `WANIPConnection` and `WANPPPConnection` service definitions, but many router implementations omit it. Treating an unsupported action as "NAT disabled" is a false negative that prevents working routers from being used. The actual port mapping operations (`AddPortMapping`, `GetExternalIPAddress`) are more reliable indicators of device capability.

### Why Return the Assigned Port?

IGDv2's `AddAnyPortMapping` allows the router to assign a different external port than requested. Returning the actual assigned port enables correct ENR (Ethereum Node Record) updates and accurate peer advertisements.

## Backwards Compatibility

- The `--nat upnp`, `--nat any`, `--nat pmp`, and `--nat extip:<IP>` CLI flags continue to work identically.
- The `--nat` default value (`any`) is unchanged.
- Nodes that previously worked with UPnP continue to work. Nodes that previously failed due to narrow search targets, SOAP action intolerance, or firewall-blocked multicast may now succeed.
- The `nat.Interface` Go API changes `AddMapping`'s return type. This is an internal interface with no external consumers outside the `p2p/nat` package.

## Test Cases

1. **SSDP multicast discovery**: Fake IGD responds to M-SEARCH on multicast address. Device is discovered and WANIPConnection service is matched (existing `TestUPNP_DDWRT` test).
2. **InternetGatewayDevice target**: Router that only responds to `InternetGatewayDevice:1` (not `WANConnectionDevice:1`) is discovered via the expanded search targets.
3. **GetNATRSIPStatus unsupported**: Device returns SOAP fault 401. Device is accepted and port mapping proceeds.
4. **GetNATRSIPStatus returns false**: Device explicitly reports NAT disabled. Device is rejected.
5. **AddMapping error propagation**: `internalAddress()` failure is returned to the caller, not swallowed.
6. **Port conflict retry**: First `AddPortMapping` attempt fails. Subsequent retry with same port or random port succeeds.

## Reference Implementation

The reference implementation modifies the following files:

- `p2p/nat/natupnp.go` — Custom SSDP discovery, tolerant NAT check, AddAnyPortMapping, retry logic, comprehensive logging
- `p2p/nat/nat.go` — Updated Interface (AddMapping returns uint16), improved Map() logging
- `p2p/nat/natpmp.go` — Updated AddMapping signature to return assigned port
- `p2p/server.go` — NAT setup logging for operator visibility
- `go.mod` / `go.sum` — goupnp v1.0.3 → v1.3.0

## Security Considerations

- **UPnP trust model**: UPnP port mapping trusts any device on the local network to open ports on the router. This is an inherent property of the UPnP protocol and is unchanged by this PIP. Node operators on untrusted networks should use `--nat none` or `--nat extip:<IP>` with manual port forwarding.
- **Unicast SSDP**: Sending M-SEARCH directly to the gateway reveals the node's interest in port mapping to the gateway device. This is no different from the multicast case, where the same information is broadcast to the entire local network.
- **Random port fallback**: When the requested port is unavailable, the node may be mapped on a random high port (10000-65535). The node's ENR is updated to reflect the actual port, so peers can still connect. Operators who require a specific external port should use manual port forwarding.
